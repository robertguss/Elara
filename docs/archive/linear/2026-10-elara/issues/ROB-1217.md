## Original scope and historical record

Discovered in ROB-1083 (LAB-3 step 4, 2026-10-02) on the owner's M3 Max.

The supplementary N=500 attribution profile at eaa88f9 failed the `users_ok` run check, and its activation ran 133.7 s late (a1 = 613,708 ms vs 480,000 registered; interior 0 ms). Neither cause can be recovered from the evidence:

* `lib/elara/lab/scenarios/concurrency.ex:479` keeps each abnormal user exit reason in `run.user_failures`, but the result emits only `users_ok` (`:1135`). The reasons are lost.
* The pre-activation census itself started at 613,698 ms and took about 1 ms, so the delay happened before it, somewhere in the scheduling of the window start under N=500 load. The BEAM was at about 1,000–1,270% CPU and external processes were small.

Why it matters: a registered N=500 profile cannot be ranked without understanding or removing these failures, and any rerun would hit the same blind spot. Evidence: lab/results/concurrency/20261002T210908440701Z-sweep-sessions-seed42/ (untracked, owner's Mac).

Acceptance: the result emits bounded, typed user-failure reasons and the profile-activation scheduling timestamps (due vs fired), with tests that fail first; a seeded short smoke shows them populated. No change to the registered workload or the window rules.
