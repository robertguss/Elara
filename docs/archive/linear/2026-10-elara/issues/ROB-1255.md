## Original scope and historical record

Fix proposal motivated by ROB-1243's diagnosis (ROB-1252, `2e1cc79`; note 003 "SessionSup diagnosis (ROB-1243, 2026-10-03)"). Untested: nothing is built until it is selected and reviewed.

Finding: during the concurrency profile's first census, `DynamicSupervisor.which_children(Elara.SessionSup)` (lib/elara/lab/profile.ex, `census/2`) waited about 130 s behind about 326 queued `start_child` calls. SessionSup spent 99.9% of that time blocked in `:proc_lib.sync_start/2`, because OTP runs each child's `Elara.Session.init/1` inside the supervisor (lib/elara.ex:94; lib/elara/session.ex:111). So SessionSup serializes session inits, and a census routed through its mailbox inherits the backlog.

Two fix directions (pick one under review; each needs a test that fails first):
(a) Harness-only, which unblocks LAB-3: the census enumerates sessions without SessionSup's mailbox. Candidates: the `Elara.Sessions` Registry (`Registry.select`, as `Elara.Lab.Sampler` already does), or the coordinator's own record of the sessions it started. The test is a census that completes promptly while a suspended SessionSup holds queued requests. Risk: the census set must stay equivalent (sessions registered vs. supervised children; registration happens inside init).
(b) Product: move the expensive part of `Session.init/1` into `handle_continue`, so start_child returns before the slow work. This changes start semantics: callers currently get `{:ok, pid}` only after init succeeds, and a failing init returns an error rather than a crash. It is a larger change, outside LAB-3's "no product fixes" scope unless the owner decides otherwise.

Not established: whether a single `Session.init` is slow or unscheduled under load (about 395 ms per start on average, drained in two phases). That matters for (b), not for (a).

ROB-1083's option (a) says: fix once the cause is clear, then one more N=500 rerun. Direction (a) is the harness fix in that sense.
