## Original scope and historical record

Discovered in ROB-1083's N=500 instrumented rerun (26a64f1, 2026-10-03, owner's M3 Max). Evidence: lab/results/concurrency/20261003T123711789702Z-sweep-sessions-seed42/ (untracked).

At N=500 with trace=profile, the coordinator handled `profile_start` on time (480,012 ms, 1 ms after its deadline), but the pre-activation memory census only began at 612,660 ms, 132,648 ms later. Activation followed at 612,671 ms. The code between those points runs synchronously in the coordinator (`start_profile/1` → `Profiling.start/1`, including `Profile.census/1` before the memory capture; lib/elara/lab/scenarios/concurrency.ex `start_profile`). The same happened at eaa88f9 (133.7 s). In the rerun, 29 users exited `:no_client` (request_client's 30 s timeout) and the coordinator's sampled mailbox peaked near 1,700, but none of this is attributed: a blocked coordinator would produce both, and that remains unproven.

Why it matters: no N=500 attribution profile can be valid while setup takes over 30 s, so LAB-3's high-N attribution is blocked on the harness, not the product.

Acceptance (bounded diagnosis first): reproduce the stall in a scaled seeded run, or show why it does not appear, and time each setup phase with evidence. Only then propose a fix, for example moving setup off the coordinator, with a test that fails first. Changes to registered window rules are out of scope.
