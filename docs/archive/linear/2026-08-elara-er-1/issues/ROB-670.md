## Description

## Outcome

Connect one synthetic marker mutation end to end: durable controller intent → executor acceptance commit → acceptance reply → callback attempt → one external mutation → durable executor completion commit → completion reply → session tool-result fact. When a reply is lost, recover by querying durable job evidence rather than retrying or inspecting conversation history.

## Context

[ROB-668](https://linear.app/robert-guss/issue/ROB-668/er1-1-commit-stable-job-identity-digest-and-controller-intent) supplies controller intent and [ROB-669](https://linear.app/robert-guss/issue/ROB-669/er1-2-implement-the-durable-test-executor-ledger-with-submit-and-query) supplies executor proof. This issue integrates only the smallest mutation needed to demonstrate a recovery outcome the current runtime cannot produce. The marker should expose duplicate external mutation and any callback reinvocation unambiguously—for example, by recording a count/unique token rather than merely ensuring a file exists.

## Scope

* Implement a test-only non-deduplicating marker mutation with separate observable callback-attempt and external-mutation counts plus a result digest; its purpose is to expose any unsafe reinvocation rather than hide it behind idempotency.
* Route that mutating effect through the controller journal and test executor ledger.
* Persist intent before submit, acceptance before callback invocation/external mutation, and completion before reply.
* Enforce [ROB-667](https://linear.app/robert-guss/issue/ROB-667/fnd-1-freeze-the-er-1-contract-and-baseline-current-behavior) ordering: acceptance commit before acceptance reply, acceptance reply before callback attempt and marker mutation, and completion commit before completion reply.
* Map terminal executor evidence into exactly one `{:tool_result, core_ref, outcome}` fact.
* On transport loss or controller restart, query the accepting executor/ledger by job ID.
* Preserve the current direct path for nonmutating tools.
* Link controller job identity, executor receipt, and Flight Recorder effect identity sufficiently to explain the recovered result.

## Non-goals

* Productionizing the remote-worker wire protocol.
* Applying the protocol to write, edit/patch, bash, plugins, or providers.
* Generic failover, queueing, retries, workspace snapshots, or leases.
* Moving job lifecycle into `Elara.Session.Core` unless the integration proves the sidecar boundary impossible.
* Public API/schema commitments.

## Acceptance criteria

* Normal execution creates the marker exactly once and produces exactly one terminal tool result.
* Same-ID/same-digest submit/query returns existing evidence without a new admission, callback attempt, or external marker mutation; conflicting digest reuse is rejected without mutation.
* Killing/restarting the controller after intent commit does not create a second admission or external mutation; callback attempts are reported separately and an uncertain non-deduplicated callback is never reinvoked.
* Losing the acceptance reply does not cause a submit to another worker.
* Losing the completion reply recovers the completed outcome through `query(job_id)` when executor proof survives.
* A query that can prove only acceptance never reports success.
* Missing admissible causal terminal proof produces the [ROB-667](https://linear.app/robert-guss/issue/ROB-667/fnd-1-freeze-the-er-1-contract-and-baseline-current-behavior) `:indeterminate` classification with job ID, digest, workspace, and last proven state available to the operator.
* Recovery does not read or repair the transcript to decide external truth.
* Flight Recorder can link the session effect to the job and final observation.
* Existing read-only retry tests and ordinary session behavior remain green.

### Final integrated sequence

`Elara.Session.Core` remains unchanged. An explicitly configured test-only sidecar owns the integrated marker path; sessions without that option retain the ordinary path.

`Flight Recorder synced run_tool effect → controller intent commit → executor receipt → accepted commit → acceptance reply → controller accepted observation → callback-attempt commit → marker callback → append one job/digest/token record → terminal result+digest commit → completion reply → controller terminal observation commit → tool_result Core fact → JSONL ToolResult append → controller result_persisted mark`.

The controller journal migrated from schema 1 to schema 2 without losing intents. Schema 2 adds monotonic executor observations and an independent `result_persisted` bit. Accepted-attempt-0 may advance to accepted-attempt-1 or terminal; terminal observations cannot be downgraded or replaced. The migration from a real schema-1 intent database is covered directly.

### Marker and causal links

The synthetic marker is deliberately non-deduplicating: every invocation appends one independently countable JSONL record containing the stable job ID, operation digest, and fixture token. The tool context receives controller identity without changing arguments or the frozen operation digest. The persisted Job now carries the model tool-call ID only as correlation metadata; it remains absent from identity/digest derivation.

The integration test proves this chain:

* Job `effect_id` uses the live Flight Recorder recording/transition/effect index.
* The result transition's `caused_by` points back to that exact run-tool effect.
* Job ID/digest equal marker bytes, executor row, controller observation, and recovered ToolResult correlation.
* Pre-hydration recovery matches the unresolved tool call by persisted correlation and validates tool name/version/arguments, workspace, capabilities, authority, and placement before reconstructing an operation.

### Three controls

1. **No fault:** one intent, admission 1, callback attempt 1, external marker record 1, terminal commit 1, completion/result digest, one controller terminal observation, and exactly one session ToolResult.
2. **Same ID/digest replay:** duplicate submit and query return the same terminal record; a supplied callback that raises is never invoked; all counts and the single marker record remain unchanged.
3. **Conflicting digest:** same job ID with a different valid digest returns `:digest_conflict`; the supplied callback is never invoked; marker/counts remain unchanged.

### Recovery and knowledge-state evidence

* **Controller killed after intent, before dispatch:** executor query is initially unknown; pre-hydration recovery submits the same ID/digest once, continues once, appends one marker, and persists one success ToolResult. Final counts are `1/1/1/1` for admission/attempt/mutation/session result.
* **Acceptance reply lost:** durable accepted attempt-count 0 survives. Recovery addresses the same executor, performs one explicit continue, and reaches one success without resubmission/failover or duplicate mutation.
* **Completion reply lost:** executor terminal evidence and one marker survive while the controller has only accepted observation. Recovery queries terminal proof, updates the controller observation, appends exactly one success ToolResult, and never invokes the callback again.
* **Callback attempted/mutated but terminal proof absent:** reopened executor reports accepted attempt-count 1. Recovery records an indeterminate ToolResult containing job ID, digest, workspace, last proven `callback_invoked`, missing terminal evidence, and `do_not_retry_or_fail_over`. Marker remains exactly one; executor remains nonterminal; no callback is reinvoked.
* **Completion delivered before session persistence:** deterministic barrier proves terminal controller observation is durable while `result_persisted=false` and the transcript has no ToolResult. Releasing it persists exactly one result then flips the independent persisted bit.
* **Nonmutating control:** with the sidecar configured, the read tool takes the existing direct path and creates no controller intent or executor job.

All barriers report arrival and wait; no sleep establishes ordering. Recovery/result assertions use the frozen 1,000 ms observation bound.
