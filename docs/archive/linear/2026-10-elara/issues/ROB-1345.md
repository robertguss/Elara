## Description

Borrowed from Earendil's Pi Durable (per-tool replay rules). Filed 2026-10-08 at owner request and refined by Code Phone's code-level review ([https://cursor.com/agents/bc-468e058c-c9d8-5ac2-9ec5-759523783b0e](<https://cursor.com/agents/bc-468e058c-c9d8-5ac2-9ec5-759523783b0e>)).

Problem: when a session reopens after dying mid-turn, the one call that may have been running is marked `indeterminate` whatever its tool, because today's tool configuration cannot prove what that call did.

Goal: persist each call's effect class (read or mutating) at call time, with the call record. Don't derive it from today's tool table. On reopen, rerun or cleanly interrupt only calls recorded as reads. bash, write, and edit stay `indeterminate` and never rerun. Receipt-backed write recovery is unchanged. Continuing the turn automatically after repair belongs to [ROB-1346](https://linear.app/robert-guss/issue/ROB-1346/opt-in-auto-resume-of-interrupted-turns-on-a-long-lived-server).

Risk: a tool labeled as a read that isn't actually pure. That is why the class is stored with the call, and why plugins default to mutating. For reference, Pi's own built-in read, write, edit, and bash are not marked replay-safe.

Acceptance: scripted crash-mid-call tests show a recorded read rerun or interrupted with a single result in the session record, a mutating call still indeterminate, and a call recorded under an older build staying indeterminate. No real-model run. Deliver a PR for owner merge.

Rough size: S to M.
