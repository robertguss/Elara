# GEPA: paper, implementation, and Elara opportunities

Researched 2026-09-06. GEPA is most useful to Elara as a way to improve a narrowly defined, versioned artifact using measured outcomes. It also supplies a productive BEAM experiment: supervise the expensive search work, preserve its evidence, and enforce promotion rules independently of the proposing model. That is a more concrete starting point than letting the running harness continually rewrite itself.

This review read the paper's methods, results, and relevant appendices, then inspected the official implementation and selected tests. It did not reproduce the reported results. The shallow clone is `/tmp/elara-paper-research-2026-09-06/gepa`, pinned to [`0632cdb5dcc052e690eab439e1b4a7e3e9cfe407`](https://github.com/gepa-ai/gepa/tree/0632cdb5dcc052e690eab439e1b4a7e3e9cfe407), dated September 1. Downloaded code was neither installed nor executed. Paper findings, implementation observations, and Elara proposals are distinguished below.

**GEPA: Reflective Prompt Evolution Can Outperform Reinforcement Learning**, Lakshya A Agrawal et al. (17 authors), **arXiv:2507.19457**: v1 July 25, 2025; current **v2 February 14, 2026**; ICLR 2026 Oral. It optimizes prompts with weights frozen. [Paper metadata](https://arxiv.org/abs/2507.19457v2).

Table 1, Qwen3-8B, scores (%), total optimization rollouts:

| Benchmark | GEPA | GRPO | GEPA total rollouts | GRPO rollouts |
| --- | ---: | ---: | ---: | ---: |
| HotpotQA | 62.33 | 43.33 | 6,871 | 24,000 |
| IFBench | 38.61 | 35.88 | 3,593 | 24,000 |
| AIME-2025 | 32.00 | 38.00 | 1,839 | 24,000 |

HotpotQA and IFBench use 150/300/300 and 150/300/294 train/validation/test examples. AIME tests 30 questions sampled five times. Reflection cannot inspect validation contents. IFBench's winner appeared at 678 rollouts: “35×” concerns **rollouts-to-best**, not time, dollars, or full budget. [Table 1, Appendix E](https://arxiv.org/pdf/2507.19457v2#page=8).

The inspected code makes the mechanism concrete:

1. A candidate maps named components to text. The integration adapter runs the candidate, supplies per-example scores and optional trajectories, then converts those trajectories into feedback for particular components. The optimizer does not understand an arbitrary harness trace automatically; the adapter chooses what becomes learning evidence. [Adapter contract](https://github.com/gepa-ai/gepa/blob/0632cdb5dcc052e690eab439e1b4a7e3e9cfe407/src/gepa/core/adapter.py#L83-L216).
2. Candidate selection preserves alternatives that do well on different cases. Its default Pareto selector delegates to a function that removes dominated candidates and samples survivors in proportion to their appearances among case winners. This preserves specialized successes that an aggregate-best-only search could discard. [Selector](https://github.com/gepa-ai/gepa/blob/0632cdb5dcc052e690eab439e1b4a7e3e9cfe407/src/gepa/strategies/candidate_selector.py#L11-L24), [sampling implementation](https://github.com/gepa-ai/gepa/blob/0632cdb5dcc052e690eab439e1b4a7e3e9cfe407/src/gepa/gepa_utils.py#L107-L134).
3. The proposer samples parents and minibatches, deduplicates parent evaluations, builds component feedback, obtains proposed text, and evaluates children on their parents' minibatches. The engine separately owns acceptance and selection. This provides identifiable boundaries for instrumentation and alternative search policies. [Proposal pipeline](https://github.com/gepa-ai/gepa/blob/0632cdb5dcc052e690eab439e1b4a7e3e9cfe407/src/gepa/proposer/reflective_mutation/reflective_mutation.py#L286-L657).

GEPA belongs to an existing family. **EvoPrompt** uses evolutionary operators to develop a population of prompts; **OPRO** conditions proposals on previous solutions and scores; **TextGrad** propagates textual feedback through a computation graph to update text variables. They are related ideas, not aliases for GEPA. GEPA's inspected implementation combines component-specific trajectory feedback with its candidate-selection machinery. [EvoPrompt, 2309.08532](https://arxiv.org/abs/2309.08532), [OPRO, 2309.03409](https://arxiv.org/abs/2309.03409), [TextGrad, 2406.07496](https://arxiv.org/abs/2406.07496).

The current software extends beyond the original paper. `optimize_anything` accepts text or component maps, evaluator feedback, training and validation examples, and an optional held-out test set. Its evaluator is the important integration boundary; Elara would not need to become a Python application. The wrapper scores seed and selected candidates on held-out examples outside the evaluation server and search budget. Consequently, a search counter is not a complete experiment cost ledger. [Current API](https://github.com/gepa-ai/gepa/blob/0632cdb5dcc052e690eab439e1b4a7e3e9cfe407/src/gepa/optimize_anything.py#L94-L176), [test scoring](https://github.com/gepa-ai/gepa/blob/0632cdb5dcc052e690eab439e1b4a7e3e9cfe407/src/gepa/optimize_anything.py#L331-L421).

The official MCP adapter explicitly targets system prompts and tool descriptions. The repository's `gskill` guide describes generating repository bug tasks with SWE-smith and learning a skill artifact from traces and test outcomes. These are useful implementation examples; neither establishes that an optimized artifact transfers reliably into Elara. [MCP guide](https://github.com/gepa-ai/gepa/blob/0632cdb5dcc052e690eab439e1b4a7e3e9cfe407/src/gepa/adapters/mcp_adapter/README.md#L1-L32), [gskill guide](https://github.com/gepa-ai/gepa/blob/0632cdb5dcc052e690eab439e1b4a7e3e9cfe407/docs/docs/guides/gskill.md#L1-L13).

Three followups sharpen the research direction:

- **Combee: Scaling Prompt Learning for Self-Improving Language Model Agents**, Hanchen Li and 13 coauthors, **2604.04247v1**, April 5, 2026. It addresses quality loss when many reflections are aggregated together, using hierarchical aggregation, duplicated/shuffled evidence, and batch-size control. Its Terminal-Bench result is **42.4→2.4 minutes**, but accuracy changes **37.9→35.6%** against sequential ACE. That experiment learns from 60 existing traces, evaluates 29 held-out tasks across three runs, and reports costs of $0.24 versus $0.17. It is not a blanket GEPA speedup. Appendix B explicitly leaves asynchronous or partially synchronous execution open. This is the most directly relevant BEAM extension identified here. [Paper, Tables 1–2 and limitations](https://arxiv.org/html/2604.04247v1).
- **Reflection in the Dark: Exposing and Escaping the Black Box in Reflective Prompt Optimization**, Shiyan Liu and five coauthors, **2603.18388**, first March 19, current **v2 June 8, 2026**, accepted ACL SRW 2026. Its VISTA method separates diagnosis from prompt rewriting, labels hypotheses, and tests alternatives. It exposes sensitivity to defective output schemas and reflector assumptions. Its strongest results concern particular seeds on GSM8K/AIME; the paper explicitly limits conclusions for reasoning models and other domains. The transferable idea is to record the claimed failure cause separately from the proposed change and measured outcome. [Current paper](https://arxiv.org/html/2603.18388v2), [version and venue](https://arxiv.org/abs/2603.18388v2).
- **RLMOpt: Adaptive Prompt Optimization via Recursive Language Models**, **2608.10471v1**, August 11, 2026, connects model-controlled search with deterministic evaluation and candidate-selection rules. Baseline/finalization evaluations sit outside its search budget. [Method and budget definitions](https://arxiv.org/html/2608.10471v1#S3).

Combee already exists in the inspected GEPA code. `ComBEEReflectionLM` duplicates records, shuffles them, produces grouped proposals, and synthesizes those proposals. Small batches fall back to one reflection call. The guide describes two batched waves when the model transport supports them, and sequential behavior otherwise. Selected tests cover structure and reuse of completed map calls after a failed reduce wave; these were read, not run. [Implementation](https://github.com/gepa-ai/gepa/blob/0632cdb5dcc052e690eab439e1b4a7e3e9cfe407/src/gepa/proposer/reflective_mutation/combee.py#L325-L445), [transport and costs](https://github.com/gepa-ai/gepa/blob/0632cdb5dcc052e690eab439e1b4a7e3e9cfe407/docs/docs/guides/combee.md#L140-L167), [failure test](https://github.com/gepa-ai/gepa/blob/0632cdb5dcc052e690eab439e1b4a7e3e9cfe407/tests/test_combee_reflection_lm.py#L1195-L1251).

For a later Elara experiment, I would choose one artifact and one failure class: for example, descriptions governing read/edit/write selection on disposable repository tasks. Freeze the candidate surface, provider/model settings, examples, and scorer. Compare task outcomes, unnecessary calls, and instruction compliance, keeping a final set of examples outside both proposal generation and repeated selection. Human corrections and actual tool failures can provide feedback; an optimizer's explanation of its own improvement is not evidence that it improved.

Elara's handoff is currently an extractive index with references and refreshed live state, so there is no existing LLM summarizer prompt for GEPA simply to tune. Candidate changes could instead target wording or evidence-selection policy, while preserving authority labels and source references. For a handful of deterministic policy options, direct enumeration is simpler than reflective search. Any later learned summarization would be a distinct product decision. [Existing handoff](../../lib/elara/session/handoff.ex#L267-L332), [base prompt](../../lib/elara/prompt.ex#L4-L10).

The BEAM contribution could be a durable experiment coordinator with supervised evaluation workers, explicit concurrency slots, and reservations recorded before dispatch. Each result should identify candidate, parent, model/settings, tool generation, split, scorer version, and source traces. Crashes should leave completed evaluations reusable and unresolved remote requests explicitly uncertain. A process restart alone does not make work durable or prevent duplicate paid requests. Rust could render candidate ancestry, per-case regressions, queued evaluations, and trace links as a research instrument.

Do not infer a speedup from adding processes. The current GEPA guide locates parallel evaluation at the adapter boundary; it also documents that core `max_metric_calls` can overshoot between iterations when several proposals are batched. Elara can investigate stricter reservation accounting and straggler handling, but remote model throughput and rate limits remain external constraints. An asynchronous variant must bind each result to its original candidate and prevent stale evidence from silently updating a newer one. [Parallelism and core budget semantics](https://github.com/gepa-ai/gepa/blob/0632cdb5dcc052e690eab439e1b4a7e3e9cfe407/docs/docs/guides/parallel-proposals.md#L95-L168).

The main methodological risks are selection overfitting, incomplete success criteria, weak feedback, and model-specific artifacts. A score that rewards a test string can select a prompt that satisfies the scorer without completing the task; a judge can reward plausible explanations; a passing aggregate can hide regressions on particular cases. These are design risks to check, not failures reproduced in this review. Reserve promotion for independently checked outcomes, retain the baseline, and recheck candidates when the target model or tools change.

`Elara.Provider.Scripted` supplies canned returns; it can validate budgets, cancellation, persistence, candidate isolation, and result routing. It cannot establish that a changed prompt improves a live model. Actual GEPA use therefore needs measurable examples and trustworthy feedback, plus authorization for any paid runs. A small, bounded experiment can answer a specific question without reviving the previously deferred broad benchmark program. This research neither requires nor starts that program. [Scripted provider](../../lib/elara/provider/scripted.ex#L1-L42).
