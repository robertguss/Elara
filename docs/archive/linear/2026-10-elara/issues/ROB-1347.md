## Description

Borrowed from Earendil's Pi Durable (`requestId` makes a submission exactly-once). Filed 2026-10-08 at owner request and refined by Code Phone's code-level review ([https://cursor.com/agents/bc-468e058c-c9d8-5ac2-9ec5-759523783b0e](<https://cursor.com/agents/bc-468e058c-c9d8-5ac2-9ec5-759523783b0e>)).

Problem: if a client retries or reconnects after a crash or a dropped connection, the same owner input can be submitted twice.

Goal: owner and API submissions accept an optional client `request_id`, which is stored on the inbox entry. Resubmitting with the same id and the same content returns the original submission rather than starting a second turn. Reusing an id with different content is rejected with a clear error. Pi silently returns the old submission in that case; don't copy that behavior. This extends the existing `thread_send` `message_id` behavior rather than inventing a new mechanism.

Touches: session store, protocol, reconnect path.

Acceptance: scripted tests cover a duplicate submit, a submit across restart and reconnect, a reused id with different content being rejected, and different ids producing distinct turns. No real-model run. Deliver a PR for owner merge.

Rough size: S, low risk.
