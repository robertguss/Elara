## Description

## Outcome

Apply the durable job protocol to a typed patch/edit operation with explicit preimage and postimage evidence. Prove when durable receipt establishes executor completion, when workspace evidence establishes only postcondition_satisfied or conflict, and when causal execution remains indeterminate without blind replay.

## Context

The current `edit` tool reads a file, requires one literal occurrence of `old_text`, replaces it with `new_text`, and writes the result directly. That gives useful local checks but no durable operation identity or post-crash receipt. This experiment must share the identity and conflict vocabulary established by the write experiment ([ROB-673](https://linear.app/robert-guss/issue/ROB-673/er2-1-reconcile-declarative-file-writes)), not invent a second protocol.

Begin only if GATE-1 ([ROB-672](https://linear.app/robert-guss/issue/ROB-672/gate-1-decide-er-1-continue-pivot-narrow-or-stop)) records **Continue** at the scope needed for typed mutations.

## Scope

* Define one typed patch/edit operation whose digest covers workspace identity, target path(s), exact transformation, expected preimage evidence, and desired postimage evidence.
* Preserve the current single-file literal edit as the minimum implementation unless unified-diff support is necessary to test the hypothesis.
* Classify observations for:
  * exact preimage present;
  * exact postimage present;
  * neither preimage nor postimage present;
  * ambiguous/multiple preimage matches;
  * missing/new/deleted target where represented by the operation;
  * ledger completion survives but reply is lost;
  * ledger loss after workspace mutation.
* Reuse ER-1 submit/query/digest rules and the conflict shape selected by [ROB-673](https://linear.app/robert-guss/issue/ROB-673/er2-1-reconcile-declarative-file-writes).
* If a temporary/staged write is required for atomicity, document its scope and limits.
* Reuse [ROB-673](https://linear.app/robert-guss/issue/ROB-673/er2-1-reconcile-declarative-file-writes)'s exact identity/conflict vocabulary and completed versus postcondition_satisfied distinction; exact postimage without durable receipt does not prove this job executed unless exclusive authority/fencing is proven.

## Non-goals

* A general Git client, merge engine, CRDT, or multi-repository transaction.
* Automatic conflict resolution or patch fuzzing.
* Treating a successful reverse-check alone as proof when unrelated workspace changes can produce the same bytes.
* Replacing every edit path before GATE-2.
* Shell-command reconciliation.

## Acceptance criteria

* Job identity changes when any target, transformation, expected preimage, desired postimage, workspace, or relevant authority changes.
* Exact preimage permits one execution under the accepted-job recovery rule; exact postimage is postcondition_satisfied and is not applied again, but executor completed requires durable causal receipt.
* Neither preimage nor postimage is a structured conflict or indeterminate result, never blind replay.
* Multiple literal matches preserve the current rejection behavior and produce no mutation.
* Same ID/digest cannot apply the transformation twice across process restart and lost replies.
* After ledger loss, exact declared postconditions may establish postcondition_satisfied and a safe no-reapply action, but causal job completion remains indeterminate without exclusive authority/fencing.
* Tests include a concurrent unrelated edit and show whether it can be preserved, conflicts, or invalidates automatic reconciliation.
* The Result explicitly states whether these semantics apply only to single-file edits or generalize to a bounded patch set.
* Current edit behavior remains available until GATE-2.
