## What BootstrapFewShot actually learns

`BootstrapFewShot` copies the student and teacher and requires matching predictor names, counts, and signatures. It temporarily removes the current example from the teacher's demonstrations, executes the teacher under trace capture, and uses the supplied metric to accept or reject the complete run. If no metric is supplied, success defaults to true. Accepted internal predictor inputs/outputs become augmented demonstrations. When a predictor occurs repeatedly, the implementation selects one occurrence, sampling between the final call and earlier calls. The remaining training examples supply labeled demonstrations; its variable called `validation` is **not an independent held-out set**. [Teacher mapping](https://github.com/stanfordnlp/dspy/blob/f70d08a5b934400d236078143e3704934f2d5dd1/dspy/teleprompt/bootstrap.py#L96-L146), [trace acceptance and demo construction](https://github.com/stanfordnlp/dspy/blob/f70d08a5b934400d236078143e3704934f2d5dd1/dspy/teleprompt/bootstrap.py#L148-L270).

This is weak credit assignment: a successful final answer does not independently establish that every intermediate action was correct or useful. The implementation can nevertheless turn whole-task supervision into examples for internal stages, avoiding manual labels for each stage. Its predictor lookup uses process-local object identities; those are unsuitable as durable identifiers across Elara worker restarts. These are implications of the implementation, not measured performance claims.

The selected regression test ensures each predictor samples labeled examples from the full available pool. The “effectiveness” test uses `DummyLM(follow_examples=True)` to copy a matching demonstration; it verifies the mechanism, not an improvement in a real model. [Tests](https://github.com/stanfordnlp/dspy/blob/f70d08a5b934400d236078143e3704934f2d5dd1/tests/teleprompt/test_bootstrap.py#L49-L113).

## MIPROv2 separates proposal generation from combination search

MIPROv2 first bootstraps candidate demonstration sets, then proposes instruction candidates, then searches their combinations. Its Optuna study uses a multivariate TPE sampler and categorical instruction/demo indices per predictor. It evaluates the baseline, samples validation minibatches, periodically fully evaluates promising combinations, and retains a best program. The search therefore operates over a prepared set of alternatives; it does not repeatedly rewrite the whole program from fresh failure feedback in the manner of GEPA's reflective search. [Stages](https://github.com/stanfordnlp/dspy/blob/f70d08a5b934400d236078143e3704934f2d5dd1/dspy/teleprompt/mipro_optimizer_v2.py#L229-L275), [search](https://github.com/stanfordnlp/dspy/blob/f70d08a5b934400d236078143e3704934f2d5dd1/dspy/teleprompt/mipro_optimizer_v2.py#L507-L692), [categorical parameters](https://github.com/stanfordnlp/dspy/blob/f70d08a5b934400d236078143e3704934f2d5dd1/dspy/teleprompt/mipro_optimizer_v2.py#L752-L798).

Without an explicit validation set, MIPROv2 slices approximately 80% from the training list's tail, capped at 1,000 examples. A trial count excludes the separate proposal/bootstrap work and is not a token or monetary cap. The study is created without a persistent storage backend; candidate logs are not a durable running-job protocol. [Split](https://github.com/stanfordnlp/dspy/blob/f70d08a5b934400d236078143e3704934f2d5dd1/dspy/teleprompt/mipro_optimizer_v2.py#L319-L334), [study creation](https://github.com/stanfordnlp/dspy/blob/f70d08a5b934400d236078143e3704934f2d5dd1/dspy/teleprompt/mipro_optimizer_v2.py#L658-L688).

The instruction proposer can use examples, a dataset summary, and descriptions of the containing program and module. This is a concrete improvement over optimizing isolated prompt wording with no account of its role. It also means proposal quality depends on the accuracy of those generated descriptions. [Grounded proposal context](https://github.com/stanfordnlp/dspy/blob/f70d08a5b934400d236078143e3704934f2d5dd1/dspy/propose/grounded_proposer.py#L144-L221).

## DSPy's GEPA adapter supplies the program boundary

DSPy discovers ordinary predictors and Flex modules, seeds their instruction/source text by component path, delegates search to GEPA, and rebuilds a new program from the selected candidate. Omitting `valset` reuses training examples for selection; the implementation explicitly distinguishes that overfitting mode from generalization. `teacher` is unsupported. `max_reflection_cost` is rejected, and custom reflection must use DSPy's proposer hooks rather than assuming standalone GEPA's template hook applies. [Compilation](https://github.com/stanfordnlp/dspy/blob/f70d08a5b934400d236078143e3704934f2d5dd1/dspy/teleprompt/gepa/gepa.py#L547-L696), [unsupported options](https://github.com/stanfordnlp/dspy/blob/f70d08a5b934400d236078143e3704934f2d5dd1/dspy/teleprompt/gepa/gepa.py#L505-L513).

The adapter deep-copies candidate programs. Predictor-specific feedback may guide reflection, but a differing predictor-specific score is replaced with the **whole-program score**. Trace selection matches signature equality and chooses an occurrence; it should not be mistaken for independent causal attribution to a named operation. [Binding](https://github.com/stanfordnlp/dspy/blob/f70d08a5b934400d236078143e3704934f2d5dd1/dspy/teleprompt/gepa/gepa_utils.py#L219-L234), [feedback extraction](https://github.com/stanfordnlp/dspy/blob/f70d08a5b934400d236078143e3704934f2d5dd1/dspy/teleprompt/gepa/gepa_utils.py#L378-L468).

Candidate-level and example-level evaluation share `num_threads`: the adapter divides the available workers, preserves context, and returns ordered results. Its checkpoint contribution saves RNG state. Ordinary traced evaluation also preserves batch-sized score/output arrays when failed examples disappear from trace collection. These are concrete contracts to retain in a distributed implementation. [Evaluation alignment](https://github.com/stanfordnlp/dspy/blob/f70d08a5b934400d236078143e3704934f2d5dd1/dspy/teleprompt/gepa/gepa_utils.py#L271-L293), [batching and RNG](https://github.com/stanfordnlp/dspy/blob/f70d08a5b934400d236078143e3704934f2d5dd1/dspy/teleprompt/gepa/gepa_utils.py#L323-L350). Tests exercise context propagation, allocations of `[2, 2]` and `[2, 3, 3]`, and RNG restoration. [Tests](https://github.com/stanfordnlp/dspy/blob/f70d08a5b934400d236078143e3704934f2d5dd1/tests/teleprompt/test_gepa.py#L793-L841).

## Flex makes implementation ownership explicit

Flex arrived as experimental functionality in 3.3.0. The official documentation says both its API and serialization format may change. That status matters: this is a promising research reference, not a settled portability contract. [Release](https://github.com/stanfordnlp/dspy/releases/tag/3.3.0), [Flex documentation](https://dspy.ai/diving-deeper/flex/).

A Flex's state contains `module_src` and its directly assigned LM. Its baseline source uses one `Predict`, or one `RLM` when tools exist. `named_predictors()` returns nothing: its inner predictors belong to the source and are rebuilt per invocation. Consequently, another optimizer does not simultaneously tune prompts that a code replacement will overwrite. Loading source calls the binding path; it does not execute that source immediately. The next `forward` does. JSON containing `module_src` therefore carries a future program, not merely inert prompt metadata. [Flex state and ownership](https://github.com/stanfordnlp/dspy/blob/f70d08a5b934400d236078143e3704934f2d5dd1/dspy/predict/flex/flex.py#L91-L168).

The code proposer receives the component signature, available context/tools, allowed primitives, current source, and example feedback. It returns an entire module class, including internal instructions and control flow. Unlike instruction reflection, its records describe whole-program I/O; the record-building code includes all supplied trajectories, despite naming the formatted input “failures.” Broken proposal handling retains original source for non-LM exceptions, while LM errors propagate. Trace-aware scoring can receive `program_trace`; metric exceptions become failure scores. An Elara adapter should separately identify scorer outages rather than treating them as candidate defects. [Code proposal and records](https://github.com/stanfordnlp/dspy/blob/f70d08a5b934400d236078143e3704934f2d5dd1/dspy/teleprompt/gepa/gepa_flex_utils.py#L64-L194), [scoring](https://github.com/stanfordnlp/dspy/blob/f70d08a5b934400d236078143e3704934f2d5dd1/dspy/teleprompt/gepa/gepa_flex_utils.py#L197-L267).

Binding performs AST parsing and class discovery, not capability validation. Execution uses an interpreter with host bridges for provided tools and predictor calls; each invocation constructs fresh bridge state and shuts down its interpreter. `max_predictor_calls` counts calls through the predictor bridge. One such call can invoke an RLM or ReAct with internal work, while direct provided-tool calls use another bridge path. It is **not a global nested inference or tool budget**. The host checks returned fields against the declared output types. [Parser](https://github.com/stanfordnlp/dspy/blob/f70d08a5b934400d236078143e3704934f2d5dd1/dspy/predict/flex/bridge.py#L74-L84), [invocation and execution](https://github.com/stanfordnlp/dspy/blob/f70d08a5b934400d236078143e3704934f2d5dd1/dspy/predict/flex/bridge.py#L180-L325).

Selected tests check exclusion of internal predictors, preserving failed-example positions, retaining crash evidence for reflection, and propagating build/proposer infrastructure errors. These establish intended contracts; no tests or code-quality improvements were reproduced here. [Ownership and evaluation tests](https://github.com/stanfordnlp/dspy/blob/f70d08a5b934400d236078143e3704934f2d5dd1/tests/flex/test_flex_gepa.py#L114-L173), [failure tests](https://github.com/stanfordnlp/dspy/blob/f70d08a5b934400d236078143e3704934f2d5dd1/tests/flex/test_flex_gepa.py#L242-L388).

## Three bounded Elara experiments

These are original proposals, not implemented DSPy or Elara features.

1. **A trace-to-demonstration artifact.** At one chosen decision boundary, retain a few successful input/output examples with source event IDs, candidate revision, and explicit acceptance evidence. Mark them provisional until their local behavior is checked; final task success alone is insufficient. Compare the existing request against one with two curated examples on a few separate tasks. The acceptance exercise should also reject an example derived from an obsolete tool generation and distinguish an owner instruction from quoted experience. This explores useful procedural memory without automatically canonizing whole transcripts.
2. **One allowance across optimization levels.** Let a supervised coordinator admit candidate/example jobs and their nested provider requests under a shared reservation ledger. Preserve candidate ID, example ID, attempt ID, and outcome kind. A four-candidate exercise should demonstrate the same concurrency ceiling as one candidate, retain failed slots, and reconcile completed evidence after a worker interruption. Durable reservations must precede dispatch; Python thread budgets and saved RNG state do not supply that protocol. No throughput improvement should be claimed without observing the external provider's constraints.
3. **An isolated implementation slot.** Try a Flex-inspired, read-only evidence-analysis component with fixed inputs/outputs and two initially hand-authored decompositions. The replaceable artifact owns its internal prompts and operations; the surrounding Core, tool permissions, and admission rules remain host responsibilities. Execute it outside the BEAM VM, persist source/hash and interpreter/capability versions, and adopt a candidate only at an explicit boundary. Acceptance should distinguish syntax failure, wrong output, scorer outage, and cancellation, while retaining the previous working artifact. A Rust view could show the implementation change alongside its traces and regressions.

Elara's existing flight recorder, durable inbox, plugin generations, and Rust execution/projection boundaries provide starting points. The new work would be explicit candidate and example identities, authoritative outcome classification, and resumable experiment state. DSPy's copied modules, Optuna study, thread-pool futures, and per-invocation counters remain ordinary Python process state, even where selected artifacts and GEPA checkpoints can be saved.

Scripted-provider tests can prove these lifecycle and accounting contracts. They cannot show that demonstrations, instructions, or a changed decomposition improve a live model. Any later optimization needs concrete task feedback and model runs with a defined scope; none of this research starts the deferred broad benchmark program.
